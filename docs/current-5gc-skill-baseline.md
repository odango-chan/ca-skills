# 5GC Source Baseline — v1alpha4 migration boundary

**Author syntax authority:** [CA-SL v1alpha4 frozen at 7f84393](skill-language-spec.v1alpha4.zh-CN.md).

The *two* current v1alpha4-shaped PDU Session **examples** now live at `examples/skills/establish-pdu-session/` and `examples/skills/establish-pdu-session-mas/`. They are source-shape examples with explicit **NOT_QUALIFIED** Owner/Host/Compiler/Studio/5GC status, not runnable implementations. The repository path prefix `examples/` is an example collection: when constructing a BuildRequest, the virtual Skill root is still `skills/<name>` (§G.7).

The full previously runnable/draft v0.2/v1alpha1 sources were **moved unchanged** to `examples/legacy/establish-pdu-session/` (36 historical Cases and five scripts) and `examples/legacy/establish-pdu-session-mas/` (six historical Cases). Those archives retain their old scalar `call`, `with`, `reconcile`, and Script contract conventions and are **never imported into v1alpha4 builds**. The behavior reference is `ca-agent-demo`; it is not a second language authority.

The historical `lib/tools/createdsession.tool.yaml` still uses `ca-agent-demo.tool/v1`, with 12 Operations. There is **no approved corresponding `connectionagent.io/toolcatalog/v1alpha4` or `connectionagent.io/capability-contracts/v1alpha4` publication** in this repository. The MAS ToolCatalog remains unapproved and unresolved. Do not infer valid Capability membership, Effect/Scope, identity Input/Output paths, Reconcile guarantees, or Evidence from the old catalog.

The new conventional example **proposes** UDM → PCF → `UPN.CREATE_UP_SESSION` → N1/N2 transfer → asynchronous step 15 `Nsmf_PDUSession_UpdateSMContext` continuation through `SSM.SIGNAL_UE_AN` → one generic, read-only SMF session-context Observation → `UPN.MODIFY_UP_SESSION` → responsibility. The later UpdateSMContext request resumes the same pending Operation and the same Skill Invocation; Host owns the paired step 17 response obligation. The context Observation is made only after the initial SM Context exists and the Step 15 continuation has completed; it is not used for polling. Its current implementation may use the existing SMF context-query compatibility interface, but the conventional Skill does not expose that legacy naming. The generic callable/Schema/Evidence/Capability remain NOT PUBLISHED. The UPN Owner boundary also owns native SMF Step 8 UPF/session-address selection as part of N4 preparation; the Skill does not expose a separate Step 8 Script Node. The separate policy-first example retains its own per-step proof and guarded cleanup. **Neither business Owner has approved these mappings yet**, and **the old Procedure's full detail and Case expectations have not yet been proven equivalent** to the new graphs. The new `schemas/establishment-request.schema.yaml` omits unsupported G.4 `pattern` (while keeping supported range and `const` constraints). Binding paths and `urn:example` Schema/Evidence references are intentionally unqualified design candidates, not fabricated approved Owner publications. Until exact trusted Owner snapshots arrive and §45.2 Compiler/Runtime/live proofs are recorded, this migration must be treated as **NOT_QUALIFIED**.

`make verify` checks source layout/shape, local Script references/strict TypedDict bindings, and document structure with negative regression tests. It does not check external Owner/Context SourcePath types. It does not parse the full v1alpha4 YAML semantics, compile, run or qualify these examples.


Proposed business decisions, explicit approval gaps and the **36+6 NOT_RUN Case inventory** are recorded in [`examples/MIGRATION-REVIEW-v1alpha4.md`](../examples/MIGRATION-REVIEW-v1alpha4.md).
