# CA-SL 规范文档编辑准则

**性质：** 资料性编辑指南（Informative）  
**适用对象：** CA-SL 规范正文、附录及相关设计说明  
**约束边界：** 本指南不定义语言语义，不增加符合性要求；与正式规范冲突时，以规范正文为准。

## 1. 结构与标题

1. 使用陈述式标题，例如“Reconcile 的输出约束”，避免以问题、评审意见或对话作为规范条款标题。
2. 一项规范性要求应能够定位到具体章节、字段、阶段、条件和处理结果。资料性背景、设计依据及示例分别标识。
3. 已冻结版本的评审历史、修订动机和实施进展应记录在独立勘误或决策记录中，避免与现行规范条款混写。
4. 保留既有章节编号、引用、示例及规范性矩阵的稳定性；编辑性修订不得造成条款引用失效。

## 2. 术语与规范性措辞

1. 技术身份、字段名、Outcome、诊断代码和 Schema 引用使用规范中已定义的原始拼写。
2. 强制性要求使用“必须”“不得”；建议性要求使用“应当”“不建议”；许可性要求使用“可以”。英文规范性关键字遵守 RFC 2119 / RFC 8174。
3. 优先使用可验证的表述，例如“缺少受信绑定时拒绝链接”，避免“系统应该知道”“实际可能会猜测”等非确定性表述。
4. 区分 Compiler 构建期、Runtime 执行期以及 Owner 发布责任。不同阶段的结论不合并为笼统的“通过”或“失败”。

## 3. 行文与示例

1. 优先按“适用条件—要求—异常处理—依据条款”的顺序写作。多个独立要求分段表述。
2. 采用中性、准确的技术语言，避免宣传式评价、情绪化措辞、修辞性问题和重复强调。
3. 示例明确标注资料性或规范性效力。教学用 Owner ID、Schema URI 和 Fixture 不视为已发布的真实契约。
4. 交叉引用优先指向规范条款；诊断映射、路由矩阵和符合性用例不应因编辑调整而变化。
5. 文档一致性检查不等于 Compiler、Studio、Runtime、Owner 或真实系统的符合性验收。

## 4. 编辑性修订检查

编辑性 PR 应至少核对以下事项：规范性关键字含义不变；YAML/EBNF/CEL/Python 示例字节不变；SourcePath、字段名、Outcome 与诊断代码不变；原有测试预期不变；表格与引用仍可解析。无法证明属于纯编辑性变更的内容应按 §45.1 的变更分级重新评审。
